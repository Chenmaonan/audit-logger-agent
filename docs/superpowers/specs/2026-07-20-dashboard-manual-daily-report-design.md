# Dashboard 隐藏入口手动发送飞书日报设计

日期：2026-07-20

状态：已确认，待实施

## 1. 背景

系统已在北京时间每天 10:00、17:00 自动发送一张全局飞书日报，但当前没有面向业务人员的即时发送入口。现有可用方式要么只能读取 `/report/daily` 的 JSON，要么需要进入 Dokploy 或容器执行命令，操作路径过长，不适合日常使用。

本设计在现有 Dashboard 中增加一个“公开展示但不明显提示发送能力”的入口。管理人员知道入口位置后，可以通过网页确认并立即发送截至当前时刻的全局日报，无需进入部署平台、容器或输入密码。

## 2. 已确认决策

- 使用 Dashboard 顶部的“飞书通知正常”状态标识作为入口。
- 状态标识正常展示绿色圆点、纸飞机图标和状态文字，不显示“发送”“触发”等功能提示。
- 不提供暗示发送能力的悬浮说明。
- 点击状态标识后进入服务端渲染的确认页面，不引入前端脚本。
- 手动日报统计北京时间当日 00:00 至点击确认时刻的数据。
- 飞书卡片完全复用自动日报的标题、配色、结构和业务文案。
- 卡片中不显示“手动”“人工触发”等来源标记。
- 卡片时间使用实际统计截止时刻，例如 `全局汇总 · 14:35`。
- 手动发送使用独立去重语义，不占用、不修改 10:00、17:00 定时时段。
- 北京时间 10:00、17:00 前后 5 分钟禁止手动发送，避免短时间收到两张内容接近的日报。
- 同一分钟内最多成功入队一次，防止重复点击。
- 不新增密码、登录框或管理端操作要求。

## 3. 目标与非目标

### 3.1 目标

1. 管理人员可在 Dashboard 内完成一次即时日报发送。
2. 入口在页面中自然展示，但不通过明显文案暴露发送功能。
3. 手动日报覆盖全部 Agent，统计窗口为北京时间当日 00:00 至确认时刻。
4. 手动日报与自动日报保持一致的卡片视觉和内容结构。
5. 连续点击、重复提交和多实例并发不能产生多张同一分钟日报。
6. 手动发送不能阻止或改变后续 10:00、17:00 自动日报。
7. 页面必须如实反馈已发送、已进入队列或发送失败。

### 3.2 非目标

- 不实现飞书群内 @机器人或关键词查询。
- 不把手动发送入口放入 Dokploy、容器命令或独立管理后台。
- 不开放无需页面确认的公开发送 API。
- 不改变自动日报的时间、统计规则和时段持久化逻辑。
- 不改变即时 high/critical 告警规则。
- 不在飞书卡片中区分自动发送和手动发送。
- 不把视觉隐藏当作权限控制；该设计只降低普通用户误触概率。

## 4. Dashboard 交互

### 4.1 隐藏入口

Dashboard 顶部状态区增加或复用飞书通知状态标识：

```text
●  ✈  飞书通知正常
```

规则：

- 飞书 `live` 且日报调度 active 时显示正常状态。
- `disabled`、`dry-run` 或状态读取失败时显示对应的中性或异常状态。
- 整个状态标识可以点击，但外观保持为状态展示，不使用明显的主按钮样式。
- 不显示“立即发送日报”文字，不增加提示发送功能的 tooltip。
- 状态标识的无障碍名称描述为“飞书通知状态”，不在入口处直接暴露隐藏操作说明。

### 4.2 确认页面

点击状态标识后进入：

```text
GET /dashboard/daily-report/send
```

确认页面明确展示：

- 操作：发送当前日报。
- 统计日期：北京时间当天。
- 统计范围：00:00 至当前确认时间。
- 覆盖范围：全部 Agent 与业务链路。
- 两个操作：返回、确认发送。

确认页面可以明确说明发送行为。隐藏要求只针对 Dashboard 主页面入口，不要求在进入确认页面后继续隐藏功能含义。

### 4.3 提交与结果

确认发送使用：

```text
POST /dashboard/daily-report/send
```

POST 成功处理后使用 303 返回 Dashboard，并通过页面 notice 展示结果：

- 飞书已完成投递：`日报已发送`。
- 已成功入队但仍待投递或重试：`日报已进入发送队列`。
- 同一分钟重复提交：`本分钟日报已提交，请勿重复操作`。
- 临近定时报送时段：`临近定时报送时段，请等待自动日报`。
- 飞书不可用：展示当前模式或不可发送原因。
- 构建或入队失败：展示稳定、非敏感的失败说明。

## 5. 统计窗口与卡片语义

### 5.1 手动统计窗口

以确认 POST 到达服务端的时刻为唯一时间基准：

- 日期和起点按配置的 `timezoneOffsetMinutes` 计算，当前为 UTC+8。
- `from` 为北京时间当天 00:00 对应的 UTC 时刻。
- `to` 为服务端收到确认请求的当前时刻。
- 页面打开时间只用于预览；最终卡片截止时间必须以 POST 时刻为准，避免确认页面停留造成统计范围过期。

### 5.2 卡片复用

手动发送继续调用现有全局日报统计和 `buildDailyReportPayloads` 渲染能力：

- 标题、蓝色标题栏、指标区、Top 风险、Top 工具和 Dashboard 链接全部复用。
- 无异常时继续发送正常总览。
- 零事件时继续发送“统计窗口内暂无审计事件”的正常日报卡片。
- 卡片只生成一张，继续遵守 payload 字节和组件数量限制。
- 副标题时间由实际统计截止时刻生成，例如 `全局汇总 · 14:35`。
- 不增加触发来源字段，不修改标题，不增加“手动生成”角标。

## 6. 手动发送流程

新增独立的手动日报服务能力，建议由 `notificationDigestScheduler` 暴露清晰接口：

```js
notificationDigestScheduler.runManual({ generatedAt })
```

主要流程：

```text
Dashboard 状态标识
  -> GET 确认页面
  -> POST 确认发送
  -> 校验飞书 live 状态
  -> 校验是否处于定时时段保护窗口
  -> 计算当日 00:00 至当前时刻窗口
  -> 查询全局统计
  -> 构建一张正常日报卡片
  -> 使用手动去重键写入高优先级 Outbox
  -> 立即请求一次 Outbox flush
  -> 303 返回 Dashboard 并展示结果
```

该流程不 claim `audit_notification_digest_slots`，也不写入定时日报时段状态。

## 7. 去重与定时时段保护

### 7.1 手动去重键

手动发送使用与定时日报不同的命名空间：

```text
feishu_daily_manual:YYYY-MM-DD:HH:mm
```

其中日期和分钟均按 UTC+8 计算。效果：

- 同一分钟内重复 POST、浏览器重复提交或多个服务实例并发，只能成功新增一个 Outbox 事件。
- 下一分钟允许再次手动发送。
- 定时日报继续使用原有日期加时段去重键，两者互不占用。

### 7.2 定时时段保护

以下北京时间区间禁止手动发送：

- 09:55:00—10:05:00。
- 16:55:00—17:05:00。

区间判断以 POST 到达服务端的当前时刻为准。被拦截的请求不生成卡片、不写 Outbox，也不改变定时时段状态。

## 8. 状态与错误处理

- 飞书模式不是 `live`：拒绝真实发送，页面展示稳定说明。
- 日报通知未启用：拒绝发送，不进入 Outbox。
- 处于定时时段保护窗口：拒绝发送并建议等待自动日报。
- 统计查询失败：不入队，返回失败 notice，内部记录诊断日志。
- 卡片构建失败：不入队，返回失败 notice。
- 去重冲突：视为重复操作，不作为系统错误。
- 入队成功但即时 flush 失败：Outbox 保持 pending，页面提示已进入发送队列，由现有重试机制继续处理。
- 飞书投递失败：继续使用现有重试和 dead-letter 机制，不向页面暴露 Webhook、请求正文或飞书原始错误详情。
- 页面提示不能把“成功入队”误报为“已经送达”。

## 9. 页面访问边界

- GET 确认页和 POST 发送操作沿用现有 Dashboard 的访问边界和同源行为。
- GET 只展示确认页面，不产生发送副作用。
- 只有 POST 才执行入队。
- 本设计不增加密码或新的登录流程。
- 状态标识的视觉隐藏不是鉴权。只要用户能够访问 Dashboard 并发现确认页面，就可能执行发送；产品验收应接受这一明确限制。

## 10. 测试策略

### 10.1 Dashboard

- 顶部展示飞书通知状态标识。
- 主页面不出现“发送日报”“立即发送”等明显入口文案。
- 状态标识链接到正确的确认页面。
- 确认页展示北京时间日期、当前截止时间和全部 Agent 范围。
- GET 确认页不会产生 Outbox 记录。
- POST 完成后使用 303 返回 Dashboard，并展示结果 notice。

### 10.2 手动日报服务

- 统计窗口为 UTC+8 当天 00:00 至 `generatedAt`。
- 有风险、无风险和零事件均生成一张卡片。
- 卡片标题、颜色和结构与自动日报一致。
- 卡片中不存在“手动”“人工触发”等来源文案。
- 副标题显示实际截止时刻。
- 同一分钟重复执行只入队一次。
- 下一分钟允许再次发送。

### 10.3 定时任务兼容

- 手动发送不创建或更新定时 slot。
- 手动发送后，10:00、17:00 仍能正常 claim 和入队。
- 09:55—10:05、16:55—17:05 的手动请求被拦截。
- 定时任务在保护窗口内仍按原规则运行。
- 手动 Outbox 去重键与自动日报去重键不冲突。

### 10.4 模式与失败

- `disabled` 拒绝发送。
- `dry-run` 不写真实 Outbox，页面不报告已发送。
- `live` 正常入队并请求 flush。
- flush 失败时事件保持 pending，页面提示进入发送队列。
- dead-letter、重试和飞书限流行为保持兼容。
- 页面和日志不泄露 Webhook、Token、卡片请求正文或内部错误堆栈。

### 10.5 回归验证

- 执行 Dashboard、日报调度器、飞书卡片和 Outbox 相关测试。
- 执行完整离线测试套件。
- 执行 `git diff --check`。
- Docker 验证使用独立项目、独立 Volume 和 `disabled` 模式。
- 真实飞书发送和线上部署必须另行获得明确确认。

## 12. 验收标准

- Dashboard 主页面自然展示“飞书通知正常”状态标识，普通用户不会看到明显发送提示。
- 知道入口的管理人员可以点击状态标识、确认并发送一张日报。
- 日报统计范围为北京时间当日 00:00 至确认时刻。
- 飞书卡片与自动日报样式和标题一致，不标记手动来源。
- 同一分钟重复操作只产生一张卡片。
- 定时报送前后 5 分钟不能手动发送。
- 手动发送不影响 10:00、17:00 自动日报。
- 页面准确区分已投递、已入队待发送和失败状态。
- 不需要进入 Dokploy、容器或输入密码。

## 13. 回滚

- 回滚 Dashboard 状态入口、确认路由和 `runManual` 调用即可关闭手动能力。
- 保留已经入队或送达的历史 Outbox 记录，不执行破坏性数据库清理。
- 手动发送没有新增定时 slot 数据，因此回滚不影响 10:00、17:00 调度状态。
- 若上线后出现异常，可先隐藏 Dashboard 入口并拒绝手动 POST，再回滚应用版本。
