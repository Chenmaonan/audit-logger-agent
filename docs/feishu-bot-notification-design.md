# 飞书 Bot 审计通知方案

## 目标

- 即时消息只发送 `high` 和 `critical` 风险，以 `review_id` 作为审查批次，并仅在相同且非空的 `agent_id + trace_id` 内聚合；任一身份字段缺失时按 Finding 单独隔离。
- 卡片面向管理层和业务负责人，首屏先展示结论、关键数字、首要风险和其他 Top 风险，技术身份降级为辅助信息。
- 即时告警每组包含本批次全部高风险发现的名称和摘要；首屏最多展示 Top 3，其余内容保留在折叠区或同组分片中。
- 北京时间每天 10:00、17:00 发送当天 00:00 至当前时刻的累计日报；每个时段固定发送一张跨 Agent、跨 Trace 的全局管理层总览，无异常时仍发送。
- 日报只保留 Top 3 风险和 Top 5 工具，详细内容通过 Dashboard 查看；无论输入规模多大都不得拆成多张卡。
- Webhook 不进入源码、卡片、日志或 SQLite outbox。

## 架构

```text
审查批次                         日报查询
    │                               │
    ▼                               ▼
按 agent_id + trace_id 分组      跨 Agent / Trace 全局聚合
    │                               │
    └───────────────┬───────────────┘
        │
        ▼
确定性 Feishu Card Renderer
  - JSON 2.0
  - 高风险筛选
  - 文本中和与脱敏
  - 即时告警折叠 / 20 KB 分片
  - 日报固定单卡 / Top 内容截断
        │
        ▼
Outbox（只存 delivery_mode + payload + dedupe_key + priority）
        │
        ▼
EventPublisher 原子 claim 到期消息并按 delivery_mode 路由
        │
        ▼
FeishuBotClient（内存读取 Webhook）
```

`Lark-card-designer` 仅用于设计期确定信息层级、折叠规则和视觉语义。它不是 SDK，也不生成生产 JSON；运行期由项目内纯函数确定性渲染，保证可测试和可复现。

## 卡片设计

### 即时风险告警

高风险告警采用 `alert_card`，标题栏始终使用橙色，不因存在 `critical` 切换为红色或 `carmine`。存在 `critical` 时标题为“严重审计风险”，仅有 `high` 时标题为“高风险审计告警”；风险等级同时使用“严重”或“高风险”文字标签，不能只依赖色差表达。

信息顺序固定为：

1. 标题、Agent 显示名称和业务链路名称；没有链路名称时显示缩短后的 Trace ID。
2. 一句话管理层结论，说明风险总数、严重数和需要关注的范围，不推断证据中不存在的业务影响。
3. 高风险总数、严重风险数、审查窗口三个关键数字。
4. 首要风险的等级、完整名称和最多两行影响摘要。
5. 其他 Top 2 风险的等级和完整名称；首屏合计最多 3 条风险。
6. `全部风险名称与摘要（N 项）` 折叠区，保留本批次全部风险名称与摘要。
7. 北京时间范围、批次、缩短后的 Agent ID 和 Trace ID 等辅助信息。
8. 唯一主操作“查看审计详情”；Dashboard URL 缺失或非法时隐藏按钮。

### 全局管理层日报

日报采用 `ops_dashboard_card`，标题栏始终使用蓝色，不随风险等级变化。每个 10:00 或 17:00 时段只生成一张卡，汇总统计窗口内所有 Agent 和 Trace，不按身份拆卡。首屏先展示总体判断，再展示事件数、异常事件数、高风险发现数、严重风险数四个关键数字，并显示“覆盖 N 个 Agent · N 条 Trace · N 类工具”。

总体判断遵循以下规则：统计窗口内没有事件时明确显示“统计窗口内暂无审计事件。”；有事件但无异常和高风险时显示“今日未发现异常或高风险，整体运行正常。”；有异常但尚无 `high`/`critical` Finding 时说明异常事件数量并建议查看详情；存在高风险时按严重程度给出管理层结论。

有高风险时只展示排序后的 Top 3 风险；有工具调用时只展示按异常次数降序、再按调用次数降序排列的 Top 5 工具。日报不承载全量风险摘要和全量工具明细，不使用分片，也不因长内容生成第二张卡；渲染器必须截断和压缩 Top 内容，使单卡始终低于 19 KiB 安全阈值及 JSON 2.0 组件上限。完整明细统一通过唯一主操作“查看完整日报”进入 Dashboard，URL 缺失或非法时隐藏按钮。统计窗口显示为北京时间当天 00:00 至 10:00 或 17:00，17:00 日报是当天累计版本。

### 身份、时间和长内容

- 优先展示配置中的 Agent 显示名称；完整 Agent ID 只用于分组、去重和查询，卡片中仅辅助展示缩短值。
- Trace 优先展示可读业务链路名称；没有名称时展示缩短后的 Trace ID。显示缩短不得改变完整 ID 对应的业务键。
- 任一身份字段缺失时继续按 Finding 隔离，卡片显示“身份信息缺失”，不得把不同来源合并。
- 上述身份隔离仅适用于即时风险告警。定时日报必须跨身份聚合，只展示覆盖的 Agent 和 Trace 数量，不展示或暗示某一个 Agent/Trace 代表整份日报。
- 所有用户可见时间转换为 `Asia/Shanghai`，不在首屏显示原始 ISO 时间。
- 服务器或容器显示的 UTC 时间比北京时间少 8 小时只是时区显示差。调度器使用绝对 UTC 时间换算北京时间时段，不允许给时间戳手工加 8 小时、修改容器时钟或把 `TZ` 当成调度修复手段。
- 容器共享宿主机系统时钟；生产宿主必须启用 NTP/chrony 并保持时钟同步。容器 `TZ` 只可用于改善人工阅读日志，不参与调度正确性。
- 缺少摘要时显示“暂无影响摘要，请进入 Dashboard 查看详情。”
- 即时告警超过 19 KiB 默认安全阈值时，只能在同一 `agent_id + trace_id` 和审查批次内分片；每片重复显示身份、总风险数、严重数和北京时间范围，标题带 `（1/N）`。日报不得分片，必须通过 Top 截断保持单卡。
- 卡片不发送 evidence、raw_json、Prompt、错误堆栈、完整工具响应、模型内部推理、Webhook 或 outbox/HTTP 等实现文案。

## 安全门

发送模式为三态：

- `disabled`：不生成待发送 outbox 数据，不联网。
- `dry-run`：生成和校验卡片，但不写 pending outbox、不联网。
- `live`：必须同时提供 Webhook 和 `AUDIT_AGENT_FEISHU_LIVE_CONFIRM=CONFIRM_FEISHU_LIVE`。

Webhook 优先从 `AUDIT_AGENT_FEISHU_WEBHOOK_FILE` 读取，也可使用 `AUDIT_AGENT_FEISHU_WEBHOOK_URL`。生产 URL 必须是 `https://open.feishu.cn/open-apis/bot/v2/hook/<id>`，禁止重定向。发送器同时校验 HTTP 状态和飞书响应 `code === 0`。

用户提供的 Webhook 已出现在对话文本中，应在正式部署前轮换，并在飞书侧启用 IP 白名单或关键词安全策略。当前发送器未生成飞书签名字段，签名校验需在实现并验证签名支持后再启用。

## 幂等、重试和限流

- 北京时间 10:00、17:00 日报使用独立时段键，在被协调时将执行状态持久化到 SQLite，并使用时段唯一键完成原子 claim；正常执行、补发、最近错过时段和失败均可查询，不能只存在于进程内存。
- 服务启动和定时唤醒时检查最近应执行时段。时点后 30 分钟内允许补发，超过窗口则把最近错过时段记录为 `skipped_late`，不在接近下一时段时发送陈旧日报。若停机跨过多个累计时段，只处理最新时段，不为更早时段补写记录。
- outbox 使用 `dedupe_key` 防止相同批次或日报时段重复入队；日报去重键只由日期和时段确定，不包含 Agent 或 Trace。持久化时段 claim 与 dedupe 共同覆盖重启、重复启动和并发唤醒。
- EventPublisher 在投递前原子 claim 到期消息，避免重叠 flush 处理同一记录；失败后按退避规则重新进入可 claim 状态。
- 规定时点日报高于普通 callback 消息；同一优先级内按创建时间处理，避免历史普通消息积压长期阻塞日报。
- 失败沿用现有指数退避和 dead-letter。
- Feishu client 串行发送并控制在约 92 次/分钟，同时满足 5 次/秒限制。
- 日报由独立日历调度器计算北京时间下一次 10:00/17:00，不依赖容器宿主时区。
- `dry-run` 或 `disabled` 不消费既有 pending 飞书消息；恢复 `live` 后继续投递。

投递语义为 at-least-once：如果飞书已接收消息，但进程在 outbox 标记 delivered 前退出，重试可能产生重复卡片。自定义 Webhook 不提供客户端幂等键；即时告警可通过批次、Agent、Trace 识别重复，日报可通过统计日期和时段识别重复。

## 可观察性与发送 SLA

`GET /health` 只暴露排障所需的非秘密状态：飞书模式、日报是否启用、业务时区和时段、下一次 UTC/北京时间、最近时段及其状态、`trigger_type`、`delivery_slot_key`、对应时段的入队/送达时间、投递延迟、`status_error` 和 Outbox 统计。响应不得包含 Webhook、`AUDIT_AGENT_FEISHU_LIVE_CONFIRM`、Token、请求正文或卡片中的审计内容。

规定时点的主 SLA 是唯一一张全局日报在北京时间 10:00:00、17:00:00 进入高优先级 Outbox；在服务正常、无既有高优先级积压且飞书可用时，目标为 10 秒内送达。30 分钟补发属于故障恢复，不计为准点发送成功，健康状态必须明确标记为补发。

## 验证门

1. 单元测试：即时告警分组、风险门槛、critical/high 排序、Top 3、独立折叠与分片；日报跨 Agent/Trace 聚合、每时段固定单卡、无风险仍发送、零事件明确提示、Top 3 风险、Top 5 工具、长内容不超字节和组件限制；以及文本中和、北京时间边界、整点启动、30 分钟内补发、超窗错过、重复启动、Outbox claim/优先级、短 ID 显示和敏感字段排除。
2. 本地全量非 external 测试。
3. 使用完全虚构的数据生成代表性预览，至少覆盖单条 high、high/critical 混合、即时告警超长折叠与多分片、有风险全局日报、无风险全局日报、零事件全局日报和超长输入固定单卡。
4. 在执行 Docker 测试前，将构建出的卡片截图或渲染图提交给用户审核；用户未明确通过时停止后续 Docker 测试。
5. 用户通过预览后，执行 Docker 断网测试和 mock transport 测试，确认无真实请求；复用同一 Volume 重启容器，确认时段状态保留且不会重复入队。
6. 检查 `/health` 的 UTC/北京时间换算、下一时段、最近时段、补发/错过状态、最近入队/送达和投递延迟，同时确认响应不包含 Secret。
7. 检查镜像环境、历史层、日志和 SQLite，不得出现真实 Webhook。
8. 在私有非生产测试 Bot 中使用虚构数据完成真实客户端视觉验收，覆盖桌面端、移动端、即时告警折叠/展开与多分片顺序，以及有风险/无风险/零事件的单卡日报。
9. 真实客户端验收通过后，才可执行不含业务数据的受控连通性 canary 并评估启用 `live`。

第 3、4 步的本地截图或渲染图用于 Docker 前的设计审核，不等同于真实客户端视觉验收。最终视觉结论必须基于飞书桌面端和移动端的真实截图或录屏；JSON、源码、单元测试及本地模拟渲染均不能替代该证据。

回滚只需将 `AUDIT_AGENT_FEISHU_MODE` 设为 `disabled`；数据库迁移仅新增可空幂等字段，不影响原 callback 消息。
